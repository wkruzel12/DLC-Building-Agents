# Guided AI Agent Builder

The builder opens to one workspace with Look For, Verify, and Don't Include visible together. New drafts are blank; examples are placeholders. Existing authored drafts are preserved exactly, including legacy Extract/Check/Flag drafts. There are no stage tabs or learning sidebar. Optional Need Help explains evidence, permitted actions, human review, the readiness record selector, and previous readiness tests. Case materials use the existing public source viewer.

Next: Review My Instructions shows the exact authored text in order, separated only by fixed LOOK FOR / VERIFY / DON'T INCLUDE headings. Back to Edit preserves all three fields. Test My AI Agent first performs the original signed readiness operations internally, in order, and only then calls the existing full-case evaluation. Current receipts are reused; changed inputs, records, or expired receipts require the affected operations again. Failure stops the chain without inventing success. A global run lock prevents duplicate tests, edits, and navigation while requests are running.

`combined-builder.ts` maps Look For to `steps.extract`, Verify to `steps.check`, and Don't Include to `steps.flag`. The labeled review is a presentation of this structured instruction set, not a new concatenated API payload. The existing runner retains its extraction, evidence checking, case-specific decision schema, action/target safeguards, and grading. No new thresholds, exclusion rules, private answers, or automatically written instructions are added. The service's existing 10–1,500-character execution limits remain; longer drafts can be typed and saved without silent truncation, but must be shortened before testing.

How Did Your AI Perform stays in the builder and shows the server's reported grade only after checking its complete record set, unique IDs, decision validity, instruction snapshot, error count, and accuracy consistency. This check does not access the private rubric or replace a missing grade with a computed score. Existing processing-error scoring is preserved. Partial or inconsistent responses show no accuracy; readable returned evidence remains accessible and prior graded attempts stay intact. Successful attempts still populate Feedback & Results and stakeholder eligibility.

What Worked / What Needs Improvement / What to Do Next use recorded counts and existing evidence, without claiming that a mismatch proves which instruction caused it. Detailed outputs, original records, instructions used, history, and comparison remain expandable. Improve My Instructions returns to the saved fields. Below-target attempts retain the required reflection, which can now be saved through the existing learning API inside the builder. Stakeholder eligibility and acknowledgement rules remain unchanged.

## Practice tests

`POST /api/stage-test` executes exactly one stage using the shared processing functions in `src/lib/runner.ts`. Practice always uses real OpenAI processing, including when `DEMO_MODE=true`. A missing API key, invalid model, incomplete response, or provider failure returns an error, never a simulated success. Existing complete simulations retain their demo/live behavior.

Requests specify a case, an exact record ID, current instructions, stage, unique request ID, and the previous stages' signed receipts. Check receives the verified extraction and public requirements; Flag receives the verified evaluation and case-specific decision schema. Targeted decisions keep the original target-validation rules. No grading key, scoring result, or private explanation enters a practice model request or receipt.

Receipts bind successful outputs to the user/browser owner, case content, exact record, instructions, upstream test IDs, and a four-hour expiry. Altered receipts and stale or cross-user dependencies are rejected before calling OpenAI. HMAC signing uses a domain-separated key derived from the existing server-only service-role credential, or the server OpenAI credential when no service-role key is configured. Rotating the signing credential invalidates old tests. Receipts contain public evidence and student instructions; they are integrity proofs, not encrypted storage or authentication credentials.

Production requires the application's existing authorized Supabase session. Local bypass remains limited to development loopback requests. The endpoint rejects cross-origin requests, bounds request size and output tokens, limits stage concurrency to two per server instance and one per owner, and makes no automatic model retries. In-flight and short-term duplicate request IDs reuse results within an instance. Duplicate suppression is not distributed across replicas.

Tests reuse the existing durable AI-message quota: 12 requests/minute and 120/hour, shared with stakeholder generation and conversations. Production therefore needs the existing `supabase/stakeholders.sql` migration and service-role configuration. No new tables or broader database policies are needed. Practice requests do not reserve full-run attempt numbers, save scored attempts, or change the existing 15-full-runs/hour quota.

## Student progress

Instructions continue to use the existing per-case draft state. Builder navigation, selected practice record, and the last three successful tests for each stage use the same identity-scoped localStorage (local development) or sessionStorage (authenticated workspace) persistence as the current flow. They survive navigation and refresh in that browser; they do not sync between devices. Failed tests show an error and do not advance progression.

Changing instructions, choosing a different record, retesting an upstream operation, or expiring a receipt makes affected tests outdated. Earlier successful outputs remain visible as history. The combined action preserves Final Review's requirement for current successful readiness tests before the complete run. It is learning guidance in the UI, not a new security or grading boundary for the existing full-run API. Old builder views restore into the writing workspace; the review/results views and selected record use the existing per-case persistence.
